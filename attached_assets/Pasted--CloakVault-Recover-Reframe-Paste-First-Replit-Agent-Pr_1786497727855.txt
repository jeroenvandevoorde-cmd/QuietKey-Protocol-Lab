# CloakVault Recover Reframe, Paste-First: Replit Agent Prompt

## Context (read this first)

You are modifying the existing CloakVault reference implementation in this Repl. The recent OCR pipeline work shipped correctly and is verified in the field: native character whitelist, PSM 6, full-resolution rectification, per-page diagnostics. Field testing showed the binding constraint is now capture quality, not app code: tesseract silently drops faint or out-of-focus regions of a photographed page while reading the rest almost verbatim.

Decision: the editable document textarea is the recovery contract. OCR is a pluggable convenience, not a dependency. The recommended capture route is the platform's own text recognition (for example Live Text on iPhone), pasted into the textarea. The built-in tesseract path stays as an offline fallback, unchanged.

This prompt re-plumbs the Recover page around that model. It contains zero OCR engine work. A per-slot merge of multiple reads has been considered and deliberately deferred pending field numbers; do not build it.

## Scope and non-negotiable rules

- Touch only: Recover page structure and copy, the textarea/photo interaction rules, one copy-only note on the Create page, and tests for the new interaction rules.
- Explicitly frozen, do not modify: tesseract configuration, whitelist derivation, PSM, the crop UI, rectification, the adaptive threshold, the decoder and alignment logic, the grammar, the renderer, RS, crypto. No visual redesign of the crop UI. If a change would alter OCR output for a given input image, stop: it is out of scope.
- All existing tests must remain green.
- Client-side only. No backend, no new runtime network calls. No localStorage, sessionStorage, cookies, or IndexedDB. Never log seeds or keys. The TEST USE ONLY banner stays on every page.

## Task 1: Restructure Recover around the textarea

Section order on the Recover page becomes:

1. Document text (primary, always expanded). Header: "Document text: recovery reads exactly this".
2. Photos (secondary, collapsed by default). Header: "Read photos with the built-in OCR (optional)".
3. Vault Key.
4. Recover button.

Copy for the Document text section, near verbatim:

"Recovery needs only this text plus your Vault Key. Get the text any way you like: paste it from your phone's built-in text recognition (photograph the page, open the photo in your gallery app, select all the text, copy, paste here), type it out by hand, or use the built-in photo reader below. Typos and gaps are tolerated: the decoder corrects what it can and reports exact counts. Prefer on-device text recognition; avoid uploading the document to cloud OCR services."

Copy for the collapsed Photos section header area:

"Your phone's own text recognition is usually more accurate than this built-in reader. The built-in reader works fully offline as a fallback."

Everything inside the Photos section (file input, per-page cards, crop flow, diagnostics, what-OCR-sees preview) stays functionally unchanged.

## Task 2: Textarea ownership rules

The textarea has two states, held in memory only:

- linked: content is auto-rebuilt from the photo list in page order. This is the current behavior and the initial state.
- manual: the user has typed or pasted into the textarea. Any user edit or paste switches the state to manual immediately.

Rules:

- In manual state, adding, removing, reordering, or re-reading photos never modifies the textarea. This is the point of the task: pasted text must be impossible to clobber silently.
- In manual state, show a small notice with two actions. "Rebuild from photos": replaces the textarea with the concatenated OCR text and returns to linked state, behind a confirm dialog because it discards manual text. "Append OCR below": appends the current concatenated OCR text once after the existing content and stays in manual state (use case: Live Text for one page, built-in OCR for another).
- Decode always reads the textarea content verbatim. Unchanged rule.

## Task 3: Decode counts on every attempt

On every Recover attempt, success or failure, surface the decoder's existing counts in the result card: tokens read, anchors matched, slots exact, slots edit-corrected, erasures, and on failure the budget line (2t + e against 28). This must render for a paste-only flow with zero photos loaded. Where this already exists for photo flows, generalize it; where missing, add it. Surfacing only: do not change how the decoder computes anything.

## Task 4: Create page print note (copy only)

Near the Print button on the Create page, add one sentence: "Print at full quality on a laser printer if possible; draft or eco mode produces faint text that resists both cameras and text recognition." No logic changes.

## Acceptance criteria

1. Paste-only recovery works end to end with zero photos: paste text, enter Vault Key, Recover, counts shown on both success and the red failure card.
2. With manual text present, photo add, remove, reorder, and re-read leave the textarea byte-identical. "Rebuild from photos" replaces content only after confirm. "Append OCR below" appends exactly once.
3. Photo path output is unchanged: for a fixed test image, OCR text and the diagnostics line are identical before and after this change.
4. Existing suites untouched and green. New tests cover the linked-to-manual transition, the no-clobber rule, and both notice actions.
5. No new runtime network requests, verified in the devtools network tab.

## What not to do

No OCR engine changes. No merge or voting features. No crop UI redesign. No grammar or renderer changes. No touching RS or crypto. No server, no persistence. If you find yourself editing files in the OCR pipeline, stop: you have misread the task.
