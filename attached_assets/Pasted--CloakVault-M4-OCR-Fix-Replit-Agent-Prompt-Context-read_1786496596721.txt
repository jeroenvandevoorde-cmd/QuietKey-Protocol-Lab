# CloakVault M4 OCR Fix: Replit Agent Prompt

## Context (read this first)

You are modifying the existing CloakVault reference implementation in this Repl: a client-side React app with a passing crypto core, a hand-rolled RS(121,93) with erasure decoding, a template cloak engine, and a Recover page where photos run through tesseract.js into an editable textarea ("recovery reads exactly this") before decoding.

The problem is the OCR layer. A sharp, flat laser print photographed normally still produces garbled textarea output. Observed damage classes from a real photo:

1. Trailing junk fragments appended to otherwise correct lines: "a scant pinch of saffron Aa", "a small pinch of cardamom i |"
2. Leading characters lost on runs of consecutive lines: "kpeas" for chickpeas, "kwheat" for buckwheat, "mall pinch" for a small pinch
3. Whole phantom lines of junk: ": a I rr ee", "wer Se I eI"
4. Characters outside the document alphabet in the output: pipes, en dashes, colons, stray digits, mixed-case fragments

Class 4 proves the configured page segmentation mode and character whitelist are not taking effect at recognize time. Classes 1 and 3 are default auto-segmentation (PSM 3) reading borders, background, and noise as text. Class 2 is image-side (shadow, page bow, or crop) and is mitigated by rectification plus decoder tolerance, not by engine settings.

Design principle, do not fight it: the decoder is built to absorb residual damage as erasures (RS budget 2t + e <= 28). The OCR layer's only jobs are to stop injecting junk, stop losing resolution, and hand the decoder honest text. Do not add semantic correction anywhere.

## Scope and non-negotiable rules

- Touch only: the Recover page OCR pipeline, shared image utilities you create for it, the decoder's token alignment layer, and tests for these. Do not modify the crypto core, the RS implementation, the cloak grammar, the renderer, or their tests. Grammar plausibility fixes (grammar-test-0002) are a separate milestone; do not attempt them.
- All existing tests must remain green.
- Client-side only. No backend, no new runtime network calls beyond the existing tesseract.js worker assets. No OpenCV.js or other heavyweight image dependencies; implement the small amount of geometry math by hand.
- Secrets never persist. No localStorage, sessionStorage, cookies, or IndexedDB for images or text. Never log seeds or keys. The TEST USE ONLY banner stays on every page.
- Never infer a word from semantic context. An unresolvable slot is an erasure. This rule is unchanged.

## Task 1: Make tesseract parameters actually apply

- Centralize OCR in one module exposing a single worker instance. Call setParameters after worker initialization and before every recognize, on the same instance that performs the recognize. If workers are created per photo, parameters must be reapplied to each one.
- Set tessedit_pageseg_mode to PSM 6 (SINGLE_BLOCK). OCR will only ever run on a rectified crop of the document (Task 3), so PSM 6 is safe.
- Derive the character whitelist from the grammar JSON at startup: the union of every character appearing in the template's connective prose and all slot lexicons, plus "0123456789", space, period, comma, and hyphen. Do not hardcode the list. Expose its length and a content hash in diagnostics.
- Whitelist support under the LSTM engine is version dependent, so verify it empirically with an automated test: render a small canvas containing letters, digits, and pipe characters; recognize it with a letters-only whitelist; assert digits and pipes are absent from the output.
- If that test shows the whitelist is ignored, implement a post-OCR filter that strips characters outside the derived set before the textarea is populated, keep the raw OCR output available in the diagnostics panel, and show a visible "whitelist emulated in post-filter" note. The verification test then asserts the emulated path instead.

## Task 2: Preserve resolution and orientation

- Decode uploads with createImageBitmap(file, { imageOrientation: "from-image" }) so iPhone EXIF rotation is applied. Provide an HTMLImageElement fallback where the options argument is unsupported.
- Never resample the image before OCR. The only geometric operation between the uploaded file and recognize is the rectification in Task 3, and its output size is derived from the source-resolution quad, not from a fixed target.
- Log the source width and height and the exact width and height of the bitmap handed to recognize. In development, print a console warning if the rectified width is below 1200 px, since text below roughly 20 px x-height is a known accuracy cliff.

## Task 3: Crop and rectify before OCR ("what OCR sees")

- After each photo is added, show a crop step: the image overlaid with a draggable four-corner quadrilateral, defaulting to a 4 percent inset from the edges. Corners are individually draggable, ordered TL, TR, BR, BL with ordering normalized after drag, and usable on mobile (touch targets at least 32 px).
- On confirm, rectify the quad to an upright rectangle with a 4-point homography: solve the 8-DOF projective transform from the four correspondences, then inverse-map with bilinear sampling over ImageData. Output width and height come from the longer of each pair of opposite quad edges measured in source pixels, so resolution is neither invented nor discarded. A WebGL implementation is acceptable; a per-pixel JS loop is also acceptable, since a one-shot cost on a recovery flow is fine.
- Convert the rectified image to grayscale (luma). Add an optional adaptive threshold (Sauvola or mean-minus-C, window around 31 px) behind a toggle, default off.
- Display the exact grayscale or thresholded image that will be sent to OCR in a collapsible "What OCR sees" preview above the textarea. OCR runs on that image and nothing else.
- Multi-photo behavior is unchanged: each photo gets its own crop step; OCR outputs concatenate in upload order into the editable textarea.

## Task 4: Alignment tolerance for the observed damage classes

The decoder aligns canonicalized input against the template's fixed connective prose. Harden that alignment without changing the erasure semantics:

- Inserted junk tokens between expected tokens must be skippable at bounded cost, so "cardamom i" still yields the cardamom slot with the "i" discarded, and junk-only lines are consumed without derailing position tracking.
- Anchor (connective prose) tokens match at edit distance up to 1, so a clipped anchor still anchors. Slot tokens keep the existing rule: exact lexicon match, else edit distance exactly 1 to a unique candidate within that slot's own word list, else an erasure at that slot's known position.
- Add a seeded damage-model fuzz suite: start from a known rendered document, programmatically apply the four observed damage classes at configurable rates (append 1 to 3 junk characters to line ends, delete 1 to 4 leading characters on runs of consecutive lines, insert junk-only lines, sprinkle out-of-alphabet characters), then assert decode succeeds and reports t and e whenever 2t + e <= 28, and fails cleanly with counts when the budget is exceeded. At least 100 seeded cases in CI.

## Task 5: Diagnostics per photo

Extend the per-photo summary to show: source dimensions, rectified dimensions, PSM in effect, whitelist size and whether applied natively or emulated, mean tesseract confidence, OCR wall time, and, after a decode attempt: tokens read, anchors matched, slots exact, slots edit-corrected, erasures.

## Acceptance criteria

1. Parameter verification test green, on either the native whitelist path or the emulated path with its visible note.
2. Synthetic round trip: render a full document to an offscreen canvas at print-like density (x-height at least 30 px), pass it through the pipeline with a trivial full-frame crop, OCR, decode. Must succeed with erasures <= 3; report the actual counts.
3. Resolution invariant: logged recognize dimensions exactly equal rectified dimensions for every photo, and no intermediate resample exists anywhere in the pipeline.
4. Damage-model fuzz suite green.
5. Manual flow works end to end on mobile Safari and desktop Chrome: upload, crop, "What OCR sees" preview, editable textarea, Recover showing counts, or the clean red failure card with counts.
6. Existing suites untouched and green. No new runtime network requests, verified in the devtools network tab.

## What not to do

No server. No OpenCV.js. No semantic word correction. No grammar or renderer changes. No touching RS or crypto. No persistence of images or text beyond in-memory state. If you find yourself doing any of these, stop: you have misread the task.
