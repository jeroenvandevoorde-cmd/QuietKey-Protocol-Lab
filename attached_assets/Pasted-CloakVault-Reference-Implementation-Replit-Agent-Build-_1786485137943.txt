CloakVault Reference Implementation — Replit Agent Build Prompt

Context — Read This First

You are building the reference software implementation for CloakVault, a long-term Bitcoin cold-storage protocol.

CloakVault’s core concept is:

Hide your Bitcoin in plain sight.

A 24-word BIP39 seed is converted to its 32-byte entropy, encrypted under a random 256-bit Vault Key into an authenticated Recovery Capsule, and represented as an ordinary-looking human document — the Recovery Document.

Recovery requires two separate things:

1. the Recovery Document;
2. the corresponding Vault Key.

Neither is sufficient by itself.

The Recovery Document contains authenticated ciphertext, not the seed.

The Vault Key contains no Bitcoin seed.

The document may therefore be copied freely without exposing the seed, provided the corresponding Vault Key is not compromised.

This build is the protocol correctness reference implementation, covering the equivalent of Phases 2 and 3 of the CloakVault development plan:

* complete cryptographic pipeline;
* capsule creation and recovery;
* deterministic cloak encoding/decoding;
* OCR recovery path;
* Independent Recovery share format;
* self-tests;
* deterministic test-vector generation.

This is not a wallet product.

It is not a production signing device.

It is not connected to Bitcoin.

It does not contain smart-card functionality.

It does not contain KMAC/key-management functionality.

It does not communicate with a backend.

If a larger CloakVault blueprint is attached to the project, treat this prompt as the authoritative scope for this implementation. Do not expand the scope beyond what is specified here.

⸻

1. Non-Negotiable Rules

1.1 Client-side only

Everything must run locally in the browser.

There must be:

* no backend;
* no Express;
* no server;
* no database;
* no API routes;
* no cloud services;
* no analytics;
* no telemetry;
* no user accounts.

The only permitted runtime network activity is loading the explicitly required tesseract.js worker/assets.

If you find yourself adding a server, stop. You have misunderstood the task.

⸻

1.2 Secrets never persist

Never write secrets to:

* localStorage;
* sessionStorage;
* IndexedDB;
* cookies;
* URL parameters;
* browser history;
* service-worker caches;
* analytics;
* telemetry;
* server logs.

Never log:

* seed entropy;
* mnemonic;
* Vault Key;
* capsule key;
* share data;
* KMAC;
* decrypted secrets

to the console.

All application state remains in memory only.

The application must make a best-effort attempt to zero mutable secret buffers before releasing them, using mechanisms such as Uint8Array.fill(0) where practical.

Important: browser JavaScript cannot guarantee physical RAM sanitization. Do not claim that it can.

⸻

1.3 Permanent safety banner

Display this banner prominently on every page:

TEST USE ONLY. Never enter a seed that controls real funds.

The default Create flow uses the fixed test mnemonic.

Entering a custom mnemonic requires explicitly ticking a warning checkbox first.

The application must never suggest that it is suitable for protecting real funds.

⸻

1.4 Cryptography libraries

Use cryptographic primitives only from:

* @scure/bip39
* @scure/bip32
* @noble/hashes
* @noble/ciphers

Do not hand-roll cryptographic primitives.

The sole exception is the Reed-Solomon implementation described below.

Do not add another cryptography library to “make something easier.”

If a required primitive is unavailable in the specified libraries, stop and expose the issue rather than silently substituting another implementation.

⸻

1.5 Known-answer tests

Known-answer tests must come from authoritative published sources.

Never generate a KAT by running this implementation and then declaring its output correct.

If a KAT fails:

Fix the implementation. Never change the expected value to match the implementation.

⸻

1.6 Deterministic randomness

Every random value must pass through one injectable RNG interface.

Production:

SystemRNG

Testing:

The deterministic test RNG must never be reachable from normal production Create flows.

Random values include:

* Capsule ID;
* AEAD nonce;
* Independent Recovery share randomness.

Tests and vector export must be completely deterministic when supplied with the same test RNG stream.

4. IMPORTANT — Do Not Invent the Production Grammar

The production CloakVault grammar is protocol material.

Do not invent a production grammar-v1.json and silently treat it as final.

If a reviewed production grammar file is supplied with the project, use it exactly.

If no production grammar is supplied:

1. create a clearly labelled grammar-test-v1.json;
2. use it to exercise the complete cloak engine;
3. make the application explicitly state that it is a test grammar;
4. do not claim that the resulting document meets the final CloakVault naturalness/capacity requirement.

The test grammar should be deliberately simple and designed to stress:

* encoding;
* decoding;
* capacity;
* OCR;
* erasure handling;
* collision handling;
* Reed-Solomon correction.

The production human-quality recipe grammar will be designed separately.

This separation is intentional.

5. Cloak Philosophy

The Recovery Document is a real ordinary-looking human document.

For example, it may be a recipe.

If it is a recipe:

* the recipe must actually make sense;
* ingredients must be plausible;
* quantities must be plausible;
* cooking methods must make sense;
* prose must be natural;
* connective language must be natural;
* the document should not feel machine-generated.

The visible document must not merely be grammatically correct.

It must be plausibly ordinary.

⸻

6. Absolute Cloak Rule

The visible Recovery Document must contain no overt technological or cryptographic information.

It must not contain terms or obvious references such as:

* CloakVault;
* Bitcoin;
* wallet;
* seed;
* mnemonic;
* key;
* encryption;
* cryptography;
* computer;
* software;
* capsule;
* QR;
* code;
* generation;
* fingerprint;
* recovery;
* vault;
* technical identifiers;
* hexadecimal strings;
* unusual machine-readable markers.

Do not add technical headers.

Do not print a Vault ID.

Do not print a generation number.

Do not print a wallet fingerprint.

Do not print a creation date for cryptographic purposes.

Do not print instructions for the device.

The Recovery Document should simply look like an ordinary document.

⸻

7. Important Separation of Responsibilities

The Recovery Document does NOT need to explain itself.

The Estate/Recovery documentation of the eventual product will identify the relevant physical objects.

The device will verify the cryptographic identity after successful recovery.

The Recovery Document itself should contain only the ordinary-looking document.

Therefore:

Do not embed human-readable technical metadata into the visible document.

The metadata required for the cryptographic protocol remains inside the encrypted capsule/header.

⸻

8. LLM Rule

There must be no LLM anywhere in this implementation.

The LLM is conceptually the:

interior designer, not the architect.

An LLM may eventually be used externally during CloakVault development to:

* generate candidate recipe templates;
* improve natural prose;
* create stylistic variations;
* help evaluate plausibility.

But the LLM must never:

* encrypt data;
* encode cryptographic information;
* decode cryptographic information;
* interpret recovery data;
* correct corrupted cryptographic data;
* make probabilistic recovery decisions;
* participate in the protocol;
* be required for recovery.

The released protocol must work without an LLM.

⸻

9. Cryptographic Specification — Exact

Do not improvise these constructions.

Seed

The wallet seed is:

32 bytes of entropy

mapped to and from a:

24-word BIP39 English mnemonic

using @scure/bip39.

The implementation must:

* reject invalid word counts;
* reject words outside the English BIP39 list;
* reject invalid BIP39 checksums;
* never silently alter a user-supplied mnemonic;
* never “correct” a mnemonic.

⸻

10. Vault Key

Vault Key:

K = 32 random bytes

Generated from the injected RNG.

The Vault Key must never be rendered as a BIP39-style word phrase.

⸻

11. Capsule ID

Capsule ID:

16 random bytes

It must be unpredictable.

It must:

* never be sequential;
* never be derived from a counter;
* never be based on a timestamp;
* never be predictable from previous IDs.

Human-readable aliases may exist in the UI, but they are not protocol identifiers.

⸻

12. Generation

Generation:

uint32 big-endian

Initial generation:

1

⸻

13. Capsule Key Derivation

Capsule key:

HKDF-SHA256(
    ikm = K,
    salt = capsuleID,
    info =
        UTF8("CLOAKVAULT-V1-CAPSULE-KEY")
        || generation as 4 bytes BE,
    length = 32
)

Use the specified library implementation.

Do not alter:

* the salt;
* info string;
* byte ordering;
* length;
* domain separation string.

⸻

14. AEAD

Use:

XChaCha20-Poly1305

from @noble/ciphers.

Nonce:

24 random bytes

Plaintext:

32-byte seed entropy

AAD:

first 21 bytes of capsule

specifically:

version (1)
||
generation (4 BE)
||
capsuleID (16)

⸻

15. Capsule Binary Layout

Exactly 93 bytes:

version        1 byte
generation     4 bytes BE
capsuleID      16 bytes
nonce          24 bytes
ciphertext     32 bytes
tag            16 bytes
--------------------------------
TOTAL          93 bytes

Do not add fields.

Do not reorder fields.

Do not silently serialize values differently.

⸻

16. Capsule Failure Behavior

These conditions must all result in the same high-level state:

RECOVERY FAILED

Examples:

* wrong Vault Key;
* altered generation;
* altered capsule ID;
* modified ciphertext;
* modified tag;
* malformed length;
* invalid version;
* invalid capsule structure.

Never reveal partial plaintext.

Never reveal a partial mnemonic.

Never attempt a “best guess.”

The cryptographic recovery result is binary:

valid exact recovery

or:

failure

17. Vault Key Text Representation

For test/development display, the Vault Key has this canonical representation:

payload = 0x01 || K
checksum = first 4 bytes of SHA-256(payload)
encoded = Crockford Base32(payload || checksum)

Group into blocks of four characters.

Prefix:

CVK1.

Reject checksum mismatches.

Never render the Vault Key as:

* BIP39 words;
* a natural-language phrase;
* a password-like sentence.

The UI must label this clearly as:

Vault Key — TEST SECRET

and warn that it is sensitive.

19. Independent Recovery Shares

Include the Independent Recovery share format in this build.

Generate:

R = 32 random bytes

Then:

Share A = R
Share B = K XOR R

Neither share alone reveals K.

Together:

Share A XOR Share B = K

⸻

Share A:

payload =
0x01
||
0x0A
||

||
shareBytes (32)

Checksum:

first 4 bytes of SHA-256(payload)

Encode using Crockford Base32.

Prefix:

CVSA1.

Share B:

0x01
||
0x0B
||
generation (4 BE)
||
shareBytes (32)

21. Share Rejoin

When rejoining:

1. validate both checksums;
2. validate both versions;
3. validate share indices;
4. ensure indices are distinct;
5. ensure generations match;
6. XOR the share bytes;
7. construct the corresponding CVK1. representation;
8. verify that it round-trips correctly.

If metadata differs, show the exact mismatched field.

Examples:

Generation mismatch.

Invalid Share A checksum.

Both inputs are Share A.

Share versions differ.

Never silently combine mismatched shares.

22. Reed-Solomon

Implement Reed-Solomon manually in:

src/lib/cloak/rs.ts

This is the only cryptographic/error-correction primitive permitted to be implemented manually.

Use:

GF(2^8)

with a clearly specified and tested field construction.

The implementation must support:

* encoding;
* errors;
* erasures;
* decoding;
* detection of uncorrectable input.

It must satisfy:

correct t errors + e erasures whenever 2t + e ≤ parity symbols.

⸻

23. Reed-Solomon Parity

Parity budget:

30% of data symbols, rounded up.

The exact deployed (n, k) values must be calculated from the actual capsule size and grammar capacity.

Do not hardcode assumptions about capacity.

The application should expose the actual deployed parameters.

⸻

24. Reed-Solomon Interleaving

Interleave the RS codeword across the document.

The purpose is to prevent localized physical damage from destroying a contiguous block of encoded symbols.

For example:

* stains;
* tears;
* OCR failures;
* folds;
* missing words.

The interleaving algorithm must be deterministic and versioned.

⸻

25. Cloak Encoding

The cloak engine operates conceptually as:

93-byte capsule
      ↓
RS encoding
      ↓
protected binary stream
      ↓
controlled vocabulary
      ↓
token sequence
      ↓
deterministic document grammar
      ↓
ordinary-looking document

The cloak is not cryptographic security.

The encrypted capsule remains the cryptographic security boundary.

27. Grammar Slot Model

The test grammar uses slots.

Each slot has:

2^k

possible tokens.

For the initial test grammar:

2 ≤ k ≤ 6

possible bits per slot.

Possible categories include:

* ingredient nouns;
* quantity expressions;
* cooking methods;
* time expressions;
* temperature expressions.

However, the final production grammar must be designed for human plausibility, not merely capacity.

28. Capacity Calculation

The build must calculate capacity dynamically from the grammar.

Do not assume the grammar has sufficient capacity.

Calculate:

required protected bits
available slot bits

At build time and at runtime in the Inspector.

If capacity is insufficient:

FAIL CLEARLY

with a message such as:

Required capacity: 968 bits
Available capacity: 912 bits
Additional capacity required: 56 bits

Do not silently truncate.

Display at least:

30. Decoder

The decoder must be deterministic.

It may:

* lowercase;
* normalize whitespace;
* strip punctuation;
* normalize line breaks;
* normalize page breaks.

It must not:

* use semantic understanding;
* use an LLM;
* infer missing words from context;
* “guess” likely recipes;
* choose between multiple possible tokens probabilistically.

⸻

31. Token Matching

For each expected slot:

Exact match

If the token exactly matches one lexicon entry:

decode it directly.

Unique edit-distance-1 match

If it differs by exactly one edit from exactly one candidate in that slot’s own lexicon:

accept it as that candidate and count it as a correction.

Anything else

Treat it as:

erasure.

Do not guess.

Do not use semantic context.

Do not choose a candidate simply because it makes the recipe sound better.

⸻

32. OCR Error Scope

The first implementation should explicitly support:

* capitalization errors;
* punctuation loss;
* whitespace variation;
* common single-character substitutions;
* unique edit-distance-1 token corruption;
* missing/uncertain tokens.

Do not silently invent complex word-merging or word-splitting heuristics.

If a photographed document produces ambiguous tokenization, the correct behavior is:

erasure or failure.

Not guessing.

51. Collision Tests

The implementation must test for:

Document uniqueness

Different payloads must not decode to the same valid capsule.

Parser ambiguity

The same document must not decode differently depending on incidental formatting.

Grammar-version ambiguity

A document produced under one grammar version must not silently decode under another grammar version.

Mutation ambiguity

A damaged document must not silently become another valid capsule.

Use fuzzing extensively.

* capsule serialization is exact;
* AEAD failure behavior is correct;
* Independent Recovery shares are correct.

Deterministic correctness

Same:

* inputs;
* RNG stream;
* grammar;
* protocol version

must produce byte-identical output.

⸻

Cloak correctness

* encoding is deterministic;
* decoding is deterministic;
* no semantic guessing occurs;
* malformed input cannot silently decode to a different valid capsule;
* capacity is calculated dynamically;
* Reed-Solomon tests pass.

⸻

OCR

At least one real photograph of a printed test document must successfully recover the original capsule with OCR-induced erasures/corrections within the configured correction budget.

⸻

Human plausibility

The printed test grammar must produce readable, coherent text.

If the grammar is explicitly marked as a prototype/test grammar, do not claim production-level human camouflage.

⸻

Security

* no secret persistence;
* no secret logging;
* no unintended network calls;
* no backend;
* no telemetry;
* no accounts.

⸻

UI

Create, Recover, Shares, and Self-Test all function end-to-end.

The UI should remain deliberately simple.

⸻

64. Final Architectural Principle

This implementation is intended to establish the boring, testable core of CloakVault.

The architecture must remain:

              BIP39 SEED
                   │
                   ▼
              VAULT KEY
                   │
                   ▼
              HKDF / AEAD
                   │
                   ▼
        ENCRYPTED RECOVERY CAPSULE
                   │
                   ▼
             CLOAK ENGINE
                   │
                   ▼
       ORDINARY HUMAN DOCUMENT

Recovery is:

ORDINARY DOCUMENT
       +
   VAULT KEY
       │
       ▼
   CLOAK DECODER
       │
       ▼
  AUTHENTICATED CAPSULE
       │
       ▼
      SEED

The cryptography must be boring.

The implementation must be deterministic.

The decoder must never guess.

The cloak must never be responsible for confidentiality.

And the visible Recovery Document must remain exactly what CloakVault promises it to be:

an ordinary piece of information that does not look like Bitcoin, does not look like cryptography, and does not look interesting.

The LLM may eventually help design that ordinary document.

It is the interior designer.

It is not the architect.

⸻

⸻

66. Most Important Instruction

When there is a choice between:

a clever implementation that appears to work

and:

a boring implementation whose behavior is completely specified and testable,

choose the boring implementation.

When a requirement is ambiguous:

do not invent cryptographic behavior.

Expose the ambiguity clearly so it can be resolved in the protocol specification.

CloakVault’s goal is not to produce an impressive demo.

The goal of this project is to produce a small, deterministic, independently reproducible reference implementation that future CloakVault hardware can be tested against.

Build the boring foundation first.

The interesting part comes later.
